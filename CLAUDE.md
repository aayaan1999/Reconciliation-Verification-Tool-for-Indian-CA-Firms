## Commands

Go is installed at `C:\Program Files\Go\bin`. If `go` is not found in a shell, put that folder on `PATH` first. Node.js 24 and npm are used only for the web UI in `web/` (React + TypeScript, Vite, Vitest, oxlint).

| Task | Command |
|---|---|
| Build all programs | `go build ./cmd/...` |
| Build for Windows from any OS | `GOOS=windows GOARCH=amd64 go build -o build/windows/ ./cmd/...` |
| Release build with the browser UI embedded | `cd web && npm ci && npm run build && cd ..` then `GOOS=windows GOARCH=amd64 go build -tags ui -o build/windows/ ./cmd/...` |
| All tests | `go test -count=1 ./...` |
| One package / one test | `go test ./internal/archtest/ -run TestEngineHasNoNetwork -v` |
| Architecture guard (no network in engine, import rules, no clock or randomness) | `go test -count=1 ./internal/archtest/ -v` |
| Validate the YAML rule store (needs Python with `pyyaml`, `jsonschema`; SPEC-002) | `cd docs/Recon_Tool_YAML_Rule_Store/recon_yaml && python tools/validate.py .` |
| Formatting check (must print nothing) | `gofmt -l .` |
| Vet (host and Windows) | `go vet ./...` and `GOOS=windows GOARCH=amd64 go vet ./...` |
| Web UI: install, test, lint, build (inside `web/`) | `npm ci`, `npm test`, `npm run lint`, `npm run build` |
| Web UI dev server | `cd web && npm run dev` |

The architecture guard evaluates both windows/amd64 (what ships) and linux/amd64, with cgo disabled. It writes `build/engine-deps-<goos>-<goarch>.txt`, which lists every package linked into `recon-engine`, and `build/engine-symbols-<goos>-<goarch>.txt`, which lists the network-package functions actually linked into the network-free commands (only parse-only ones may appear). Together they are the proof that the engine has no network code. A new import edge into a network package from a third-party library fails the guard until it is reviewed and added to `allowedNetworkImports` with a reason (ADR 0001). Every package in the module must be classified in exactly one of `engineSidePatterns`, `serverSidePatterns` or `otherPatterns` in `internal/archtest/archtest_test.go`; the guard fails on an unclassified package, so add each new package there. New deterministic packages also go in `deterministicDirs`. The guard reads all module sources, so `go test` caching cannot hide a violation, but `-count=1` is still used in CI. CI (`.github/workflows/ci.yml`) runs the format check, vet (host and Windows), tests and a Windows build on every push, plus a `web` job that runs `npm ci`, lint, tests and the production build.

All figures, PANs and entity names in the spec are illustrative. Never treat them as real client data, and never put real client data in this repo.

## What the product is

An offline consistency layer for Indian CA firms. It reads what the accounting package (Tally), the tax suite, the GST portal, TRACES and EPFO/ESIC produce, and reports every place where they disagree, to the rupee. It also flags expense and income heads that are new or missing compared with the prior year. It does not prepare filings, keep books or give tax advice (§3.2).

## Non-negotiable invariants

These come from the spec and should constrain every piece of code:

1. **Assert only what can be computed (§2).** A finding shows both values, the difference and both source locators (file + page/locator). Output never says "should", never states a correct value, and never makes an applicability or characterisation judgment. Judgment findings were wrong 6 times out of 9 in the reference review.
2. **No LLM in the finding decision path (§5.4).** An optional local model may only suggest a classification for a new ledger head (the user confirms it) or restate a finding in plain language. It may never create, suppress or alter a finding.
3. **Money is integer paise everywhere.** No floating point anywhere in money arithmetic (C4).
4. **Determinism (C4).** The same input must give the same output: no dependence on map-iteration order and no clocks or randomness in rules.
5. **The engine binary has no network capability (§4.1, C3).** The reconciliation engine must never contain code that can open a connection or resolve a name. Our own code must never import `net`, `net/*`, `crypto/tls` or `golang.org/x/net/*`. A third-party library may reach a parse-only network package (such as `net/url`) only through an import edge listed and justified in `allowedNetworkImports` (`docs/adr/0001-engine-network-proof.md`). The built `recon-engine` binary is then checked: it must link no connection, socket or resolver code. The updater is a separate process. The import-graph and linked-symbol proofs are build artefacts.
6. **Rules are data, not code (§5.2.4, C5).** Rules are declarative YAML, with Starlark as a sandboxed escape hatch. A CA who is not an engineer must be able to read them. Each rule ships with golden-file fixtures: at least one passing and one failing (§6.4, §9). A rule that fires wrongly in the field gets disabled, not tuned. Rule packs are versioned by assessment year and signed with Ed25519.
7. **Every data source needs a manual file-drop path (§8.1).** API or ODBC access is an optimisation, never a dependency, so the tool has to work fully air-gapped.
8. **Zero-install deployment (C2, C7).** One binary on one office machine, with staff using it from a browser over the LAN. No Docker, no external services (Redis and similar), no runtime prerequisites. The job queue runs in-process with its state stored in the DB.

## Planned architecture (§5, §6)

- **Stack:** Go single static binary. SQLite through the pure-Go `ncruces/go-sqlite3` driver, encrypted at rest with its AES-256-XTS VFS instead of SQLCipher (explicit SQL, no ORM; ADR 0002). A React + TypeScript UI embedded with `go:embed` (package `web`, only in builds with `-tags ui` after `npm run build`). `excelize` for Excel. Vendored Poppler 26.09.0 `pdftotext -layout` for PDFs, in `third_party/poppler/` (GPL, run as a separate program; ADR 0003). Its test runs only on Windows, and some sandboxed Bash shells cannot start it, so run it from PowerShell there. Where the tax suite emits JSON, prefer parsing that over its PDFs. A Python `pdfplumber` sidecar is a last resort only.
- **Pipeline:** ingestion adapters → normalised encrypted fact store → deterministic rule engine → findings with lifecycle and audit trail → LAN web UI.
- **Tie-out model (M2):** a *Fact* is `(artefact, locator, label, value, period)`. An *Edge* asserts that facts must be equal or must satisfy a relation. A *Finding* is a broken edge. Rule categories R1–R10 (§6.2) are the reference defect catalogue, and the Phase 1 gate is reproducing all of them with zero false positives.
- **New-head detection (M3, §7):** a year-on-year ledger diff (new, vanished, broken recurrence, step change, unmapped head). Its output is a classification *worklist*, which is separate from findings.
- **PDF extraction must preserve column layout.** Naive text extraction reorders statutory table columns and produces confident false findings. Validate every extractor against known-good fixtures.
- **UI:** exactly three screens: Season board, Client file and Worklist (§11.2). Group findings by the document that needs fixing, not by rule category. Always show the arithmetic. Keyboard-first.
