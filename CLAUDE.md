The architecture guard evaluates both windows/amd64 (what ships) and linux/amd64, with cgo disabled. It writes `build/engine-deps-<goos>-<goarch>.txt`, which lists every package linked into `recon-engine`, and `build/engine-symbols-<goos>-<goarch>.txt`, which lists the network-package functions actually linked into the network-free commands (only parse-only ones, plus the initialisers of `net` and `dnsmessage`, may appear). Together they are the proof that the engine has no network code. A new import edge into a network package from a third-party library fails the guard until it is reviewed and added to `allowedNetworkImports` with a reason (ADR 0001). Every package in the module must be classified in exactly one of `engineSidePatterns`, `serverSidePatterns` or `otherPatterns` in `internal/archtest/archtest_test.go`; the guard fails on an unclassified package, so add each new package there. New deterministic packages also go in `deterministicDirs`. The guard reads all module sources, so `go test` caching cannot hide a violation, but `-count=1` is still used in CI. CI (`.github/workflows/ci.yml`) runs the format check, vet (host and Windows), tests and a Windows build on every push, plus a `web` job that runs `npm ci`, lint, tests and the production build.

All figures, PANs and entity names in the spec are illustrative. Never treat them as real client data, and never put real client data in this repo.

## What the product is

An offline consistency layer for Indian CA firms. It reads what the accounting package (Tally), the tax suite, the GST portal, TRACES and EPFO/ESIC produce, and reports every place where they disagree, to the rupee. It also flags expense and income heads that are new or missing compared with the prior year. It does not prepare filings, keep books or give tax advice (§3.2).

## Non-negotiable invariants

They live in `.claude/rules/project-invariants.md`, which is always loaded: assert only what can be computed (a finding shows both values, the difference and both source locators, never "should" or a correct value); no LLM in the finding decision path; money is integer paise; determinism; no network capability in the engine (ADR 0001); rules are data with pass and fail fixtures; a manual file-drop path for every source; zero-install deployment; offline always; no real client data. `.claude/rules/security-and-privacy.md` adds the data-handling rules.

## Planned architecture (§5, §6)

- **Stack:** Go single static binary. SQLite through the pure-Go `ncruces/go-sqlite3` driver, to be encrypted at rest with its AES-256-XTS VFS instead of SQLCipher (decided in ADR 0002, not yet wired in: `store.Open` opens a plain file until SPEC-034; explicit SQL, no ORM). A React + TypeScript UI embedded with `go:embed` (package `web`, only in builds with `-tags ui` after `npm run build`). `excelize` for Excel. Vendored Poppler 26.09.0 `pdftotext -layout` for PDFs, in `third_party/poppler/` (GPL, run as a separate program; ADR 0003). Its test runs only on Windows, and some sandboxed Bash shells cannot start it, so run it from PowerShell there. Where the tax suite emits JSON, prefer parsing that over its PDFs. The tool uses no Python, not even a PDF sidecar (decided 28 October 2026, §5.2.5).
- **Pipeline:** ingestion adapters → normalised encrypted fact store → deterministic rule engine → findings with lifecycle and audit trail → LAN web UI.
- **Tie-out model (M2):** a *Fact* is `(artefact, locator, label, value, period)`. An *Edge* asserts that facts must be equal or must satisfy a relation. A *Finding* is a broken edge. Rule categories R1–R10 (§6.2) are the reference defect catalogue, and the Phase 1 gate is reproducing all of them with zero false positives.
- **New-head detection (M3, §7):** a year-on-year ledger diff (new, vanished, broken recurrence, step change, unmapped head). Its output is a classification *worklist*, which is separate from findings.
- **PDF extraction must preserve column layout.** Naive text extraction reorders statutory table columns and produces confident false findings. Validate every extractor against known-good fixtures.
- **UI:** three working screens, Season board, Client file and Worklist (§11.2), plus Rules, the read-only start of the Rule Builder screen (Build Plan module 13; decided 15 October 2026, SPEC-004 part 6). Group findings by the document that needs fixing, not by rule category. Always show the arithmetic. Keyboard-first.
